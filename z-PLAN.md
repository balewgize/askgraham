# askgraham — Migration & Build Plan

A production-grade RAG portfolio project. Reader stays, backend gets rebuilt in Python.

**Status:** Phase 1 complete (monorepo restructure), uncommitted. Phase 2 in progress —
backend foundation is running (`/healthz` green, 16 tests passing).

---

## 1. Goal

Turn a static Next.js essay reader into a deployable RAG application that demonstrates
retrieval engineering with *measured* numbers — the thing most RAG portfolios cannot show.

Target: AI/ML engineering interviews. Live URL, public repo, eval results, write-up.

---

## 2. Architecture decisions

Confirmed in discussion. Rationale recorded so they survive future disagreement.

| # | Decision | Chosen | Why | Alternative rejected |
|---|---|---|---|---|
| 1 | Rendering model | Static prerender from backend, via a committed **snapshot** | Keeps SEO + LCP; hermetic builds | Runtime fetching (hurts SEO, couples reader to backend uptime) |
| 2 | Storage | **Postgres + pgvector** | Industry standard; one DB for relational + vector + full-text, so hybrid RRF is a real story | SQLite+sqlite-vec (weaker prod story), Qdrant (second datastore) |
| 3 | Embeddings | **Local ONNX via `fastembed`** (`bge-small-en-v1.5`) | Zero marginal cost, reproducible evals, no API key in the retrieval path, no torch | Hosted embeddings (costs money per eval run, results drift) |
| 4 | Deployment | **Local-first now**, split free hosting decided at Phase 10 | Keeps the surface area small while the RAG features land | Committing to hosts before the app works |

### The snapshot decision

Decision 1 was originally "prerender by calling the API at build time." Free hosting
forced a change:

- Google Cloud Run **scales to zero** → every Vercel build would hit a cold start.
- Vercel Hobby builds from **forks have no access to secrets** → no `BACKEND_URL`.

Revised flow:

```
uv run python -m rag.snapshot → queries Postgres → writes frontend/snapshot/*.json
git add frontend/snapshot   → committed, versioned
next build                  → reads snapshot/*.json, zero network
runtime                     → API only for chat / search / summaries
```

The snapshot is still generated by the backend, so single-source-of-truth holds. Builds
become hermetic and reproducible; the backend only needs to be awake for actual chat traffic.

## 3. Target structure

```
askgraham/
├── backend/                     Python code lives directly here (no src/, no wrapper pkg)
│   ├── pyproject.toml           [tool.uv] package = false
│   ├── uv.lock
│   ├── Dockerfile
│   ├── alembic.ini
│   ├── alembic/{env.py, script.py.mako, versions/}
│   │
│   │   Only entrypoints and the settings leaf stay at the root; everything
│   │   else is a package. Recorded in docs/adr/0001-backend-module-layout.md.
│   │
│   ├── main.py                  FastAPI app factory + middleware
│   ├── config.py                pydantic-settings + BACKEND_DIR / REPO_ROOT
│   ├── cli.py                   ingest / index / summarize / eval
│   │
│   ├── core/                    db.py · models.py · logging_config.py · errors.py
│   ├── rag/                     ingest · chunking · embeddings · retrieval · snapshot
│   ├── llm/                     llm · generation · summarization
│   │
│   ├── eval/{runner,metrics,judges}.py
│   ├── eval/datasets/qa.jsonl
│   ├── eval/results/baseline.md
│   └── tests/{__init__.py, conftest.py, test_*.py}
│
├── frontend/                    Next.js 16 (unchanged until Phase 3)
├── data/                        233 essays + metadata (git-committed)
├── docs/                        architecture.md, adr/
├── docker-compose.yml
├── Makefile
└── README.md
```

**Naming notes**
- `data/` over `content/` — the directory holds essays *plus* config and derived metadata,
  so "content" was slightly wrong. Conventional, accurate, less git churn.
- `embeddings.py` split from `llm.py` — different providers and failure modes.
  `rag/embeddings.py` = local ONNX (free, offline).
  `llm/llm.py` = remote chat/structured output (OpenRouter, costs money, network).
  The package split mirrors the module split, so the cost and failure boundary
  is visible in the tree rather than only in import graphs.
- `eval/` inside `backend/`, not at repo root — two directories named `evals` at
  different levels is a navigation wart. Linked from the README for visibility.
- `logging_config.py`, not `logging.py` — a root-level `logging.py` sits exactly
  where the stdlib `logging` module resolves from, and stays a grep hazard
  regardless of which package it lives in.

## 4. Phases

One phase at a time. Stop and review after each.

### Phase 1 — Monorepo restructure ✅
Move Next.js to `frontend/` via `git mv`, root tooling, verify build unchanged.

**Done:** 290 renames detected (history preserved). Build produces 244 static pages,
lint clean, real essay content verified in output, 233 essay links on home page.
Fixed along the way: 20 hardcoded `data/` refs collapsed into one `DATA_DIR` constant;
frontend package renamed `askgraham` → `frontend` (`--filter frontend` was broken);
duplicate lockfile deleted.

### Phase 2 — Backend foundation
`uv init`, `pyproject.toml`, `config.py`, `main.py` app factory, structlog with
request-id, `/healthz` + `/readyz`, Alembic skeleton, `Dockerfile`, `docker-compose.yml`
with `pgvector/pgvector:pg17`. `docker compose up` → healthy service.

### Phase 3 — Corpus → Postgres + API
Schema (`essays`, `footnotes`, `phases`, `reading_paths`, `path_steps`, `taxonomy`),
Alembic migration, idempotent `ingest.py` (content-hash skip), REST endpoints,
`snapshot.py`, frontend `lib/` switches from `fs` to snapshot JSON, FlexSearch removed.

### Phase 4 — LLM layer + summaries
`llm.py` with `Protocol` + OpenRouter adapter (chat + JSON-schema structured output).
Batch summaries: thesis / non-obvious ideas / key quotes.
**Verbatim quote verification** — every returned quote must appear in the source
paragraph (normalized). Reject + retry otherwise. Report the pass rate.

### Phase 5 — Chunking + hybrid retrieval
Paragraph-aware chunker with overlap, token-budgeted, retains paragraph indices for
citations. Embed to pgvector (`hnsw` index). Postgres FTS (`ts_rank_cd`) for lexical.
**RRF fusion** of both, then optional reranker. `GET /api/v1/search`.

### Phase 6 — Chat with citations
SSE streaming endpoint. Retrieval → context assembly → generation with inline citation
markers resolving to essay + paragraph. Query rewriting for follow-ups.
Rate limiting, structured logging, per-query latency + cost logging.

### Phase 7 — Evals harness ← the differentiator
`eval/datasets/qa.jsonl`: 30+ questions with gold essay + paragraph refs.
Retrieval metrics: recall@k, MRR, nDCG. Answer metrics: LLM-as-judge (faithfulness,
relevance, citation correctness) + quote-grounding check.
Reproducible: pinned model, temperature 0, seeded. Baseline → `eval/results/baseline.md`.

### Phase 8 — Tuning driven by evals
Ablations: chunk size {512/1024/2048}, overlap, hybrid vs vector-only vs lexical-only,
RRF k, reranker on/off, query rewriting on/off. Before/after table + cost + latency.
**Start from real failure cases mined in Phase 6 logs**, not a list of ideas.

### Phase 9 — Tools / agentic
`find_related_essays`, `compare_pg_on_topic`. Tool loop with streamed tool events to UI.

### Phase 10 — Hardening + portfolio polish
CI (backend lint/type/test, frontend lint/build, eval smoke test). Security headers,
CORS, rate limits. Docker hardening, non-root, model cache volume.
Free-tier deployment. README with architecture diagram + demo GIF. Write-up post.

## 5. Deployment (free tier)

Verified Oct 2026. Target decided at Phase 10.

**Recommended — 3 accounts, $0, no expiry**

| Piece | Where | Why |
|---|---|---|
| Database | **Neon** (free) | pgvector on every plan, no add-on. 0.5 GB, ample. No expiry. |
| Backend | **Google Cloud Run** (free) | 2M req/mo, 360K GB-s memory, scales to zero, Docker-native. 1 vCPU / 2 GiB. |
| Frontend | **Vercel Hobby** (free) | Next.js first-class. Builds need no backend (snapshot). |

**Alternative — 1 account, simplest story:** Oracle Cloud Always Free Ampere A1
(now **2 OCPU / 12 GB**, halved June 2026). One box, `docker compose up`, Caddy for TLS.
Tradeoffs: credit card, ARM64-only, free capacity often unavailable.

**Ruled out**

| Service | Reason |
|---|---|
| Render | Free web service capped at **512 MB RAM** — ONNX embedding model doesn't fit. Free Postgres **expires in 30 days**. |
| Koyeb | Free tier closed to new signups (Feb 2026). |
| Fly.io / Railway / PlanetScale | No free tier. |
| Neon + `pg_search` | Neon deprecated `pg_search`; existing installs must migrate by Sept 21 2026. Use `ts_rank_cd`. |

## 6. Deviation from z-IDEA.md

`z-IDEA.md` (the original 7-day plan) puts retrieval on Day 3 and evals on Day 4.

**That order is backwards for a job hunt.** Tuning retrieval without metrics means
changes can't be proven to help. Phase 7 (evals) is therefore merged conceptually
*into* Phases 5–6: write the eval harness while building retrieval, not after.

## 7. Portfolio positioning

What makes this defensible in interviews:

1. **Measured retrieval, not vibes.** Anyone can demo RAG. Almost no one ships
   recall@k / MRR / nDCG with an ablation table.
2. **Quote verification.** "How do you know the model isn't inventing quotes?" →
   "we verify verbatim against the source paragraph and report the rejection rate."
   Most candidates cannot answer this.
3. **Failure mining.** Phase 8 starts from real failures found in Phase 6 logs.
   That's how platform teams work and it reads as senior.
4. **Evals in CI.** Treating quality as a gate, not a one-off.
5. **Cost + latency per query.** Production thinking, not just a demo.
6. **"What I'd do next."** Knowing where your own system breaks is the strongest
   thing you can put in a README.
